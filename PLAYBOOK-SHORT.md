# Краткий плейбук для нового участника команды

Сокращённая версия [PLAYBOOK.md](PLAYBOOK.md). Если захочешь подробностей, примеров и бланков, смотри полную версию.

## Что мы делаем

- **Хакатон:** EHL Grand Finale (TUM.ai), 10–11 октября 2026, Science Congress Centre, Гархинг под Мюнхеном. Тема — agentic AI.
- **Что строим:** AI-агента под один из трёх челленджей партнёров (OpenAI, BMW Group, Atira). Челленджи объявят в субботу в 10:00.
- **Основа:** этот репо. Backend на FastAPI с агентом на OpenAI Agents SDK, простой чат-интерфейс.
- **Обязательно:** **Entire**. Сабмит без него не принимают (подробнее ниже).

## Подключиться за 10 минут

1. Попроси у капитана доступ к приватному репо на GitHub.
2. Установи Entire:
   ```bash
   curl -fsSL https://entire.io/install.sh | bash
   ```
3. Склонируй репо. **На Mac — не в «Рабочий стол» и не в «Документы»**, если они синхронизируются с iCloud: iCloud выгружает файлы, и проект начинает зависать.
   ```bash
   mkdir -p ~/Developer && cd ~/Developer
   git clone https://github.com/ksiox1337/ehl-finale-template.git
   cd ehl-finale-template
   ```
4. Включи Entire в репо (на каждом новом клоне):
   ```bash
   entire enable --agent claude-code
   ```
   Если пользуешься другим агентом, укажи его: `cursor`, `codex`, `copilot-cli`, `opencode`.
5. Установи зависимости и запусти:
   ```bash
   make setup
   ```
   Впиши свой OpenAI-ключ в `.env`, затем:
   ```bash
   make run
   ```
   Открой http://localhost:8000 и задай вопрос в чате.
6. Сделай тестовый коммит **через AI-агента** и убедись, что при push появилась строка
   `[entire] Pushing 1 checkpoint ref(s) to origin... done`.
7. Вступи в Discord: https://discord.gg/4UDNd5TAg

## Команда и роли

| Роль | Кто отвечает | За что |
|---|---|---|
| **A — Agent/Backend** | | Агент, инструменты, интеграция с API партнёра |
| **B — Frontend/Demo** | | Интерфейс, сценарий демо, запасное видео |
| **C — Product/Pitch** | | Пользователь, данные, тесты, питч, сабмит. Он же **Decider** |
| **Новый участник** | ты | Роль обсудим вместе. Чаще всего это данные, eval и тесты либо помощь A или B |

**Decider (C)** ставит точку, если голоса разделились или спор идёт дольше 5 минут. Правило *disagree and commit*: можно не соглашаться, но решение выполняем.

## Правила команды

1. **Таймбокс.** У каждого шага есть лимит времени. Время вышло — шаг закончен.
2. **Парковка.** Идеи «на потом» записываем в отдельный список и не обсуждаем сейчас.
3. **Сначала молча, потом вслух.** Идеи придумываем и голосуем каждый сам, потом сравниваем.
4. **Стендап раз в 2 часа**, 5 минут: что сделал, что делаю, что мешает.
5. **Застрял на 20 минут — скажи.** Не сиди молча.
6. **Меняешь план — скажи вслух**, чтобы никто не строил то, что от этого зависит.
7. **После воскресенья 09:00 — никаких новых фич**, только исправления.

## Метод: Design Sprint × ТРИЗ

Design Sprint даёт процесс принятия решений, ТРИЗ — способ найти сильную идею, а не первую очевидную. Этапы по порядку:

| Этап | Что делаем | Результат |
|---|---|---|
| **1. Карта** | Описываем конкретного пользователя и его путь в 5–7 шагах. Отмечаем шаг, где болит сильнее всего (target) | Пользователь, карта, target |
| **2. ИКР** | Формулируем идеальный результат: «[X] **сам** [делает нужное] без затрат и вреда». Записываем, что мешает его достичь | ИКР одним предложением |
| **3. Противоречие** | Ищем конфликт: «Если [делаем X], то [хорошо], но [плохо]». Затем ищем способ получить и то и другое: разнести во времени, в пространстве, по условию или по частям системы. **Компромисс не годится** | Противоречие и 3–4 идеи, как его разрешить |
| **4. Ресурсы** | Что уже есть: данные и API партнёра, наш шаблон, возможности SDK, эксперты на площадке. Плюс 1–2 существующих продукта, у которых можно что-то позаимствовать | Список ресурсов |
| **5. Скетчи** | Каждый **сам и молча** набрасывает 8 вариантов, затем рисует один подробно в 3 кадрах. Если идеи кончились, бери приёмы ТРИЗ: «наоборот», «предварительное действие», «дробление», «посредник», «самопроверка» | По одному решению от каждого |
| **6. Решение** | Молча ставим точки на понравившиеся части скетчей, голосуем, Decider выбирает. Проверка: решение разрешает противоречие или это компромисс? Нужен ли тут агент вообще? | Выбранное решение |
| **7. Storyboard** | Покадровый сценарий демо: проблема → действия → **один вау-момент** → результат с цифрой. Плюс список инструментов агента и задачи по людям | Сценарий демо и задачи |
| **8. Сборка** | Сначала **один сценарий целиком** через все слои (данные → инструменты → агент → UI), пусть некрасиво. Настоящее — только ядро, остальное — заглушки | Работающий сценарий |
| **9. Тест** | Показываем 2–3 людям (эксперт партнёра, ментор, соседняя команда), **молчим и смотрим**, где путаются. Проблемы сортируем: must / should / won't | Список исправлений |

**Тест «нужен ли агент»:** агент оправдан, если хотя бы два ответа «да». Шаги заранее неизвестны? Нужны несколько источников данных? Есть действие во внешнем мире? Входные данные неструктурированные? Нужно подстраиваться под ситуацию?

## Работа с кодом и Entire

- **Код пишем через AI-агента** (Claude Code, Cursor, Codex) в папке репо. Entire записывает сессию агента и привязывает её к коммиту.
- **Коммитит агент**: «закоммить с понятным сообщением и запушь». Коммит руками без активной сессии агента уходит без checkpoint'а.
- После push проверяй строку `[entire] Pushing N checkpoint ref(s)`.
- Если push упал с `fatal error in commit_refs`, просто повтори `git push`.
- **Мелкие коммиты, часто.** Перед push — `git pull --rebase`.
- **Делим файлы, чтобы не было конфликтов:** A — `backend/`, B — `frontend/`, C — `backend/data/` и README.
- **Никаких ключей в коде.** Только в `.env`, он в `.gitignore`.
- Не пушь ветки `entire/*` вручную.

**Как устроен проект:**
- Агент — в `backend/app/agent.py`, инструменты — в `backend/app/tools.py`.
- Новый инструмент: функция с типами и описанием (docstring), декоратор `@tool`, добавить в `ALL_TOOLS`.
- В описании инструмента пиши, **когда** его использовать: модель выбирает инструменты по описанию.
- Ошибки в инструментах возвращай строкой с подсказкой, а не исключением.

## Демо и питч

- Демо начинаем как можно раньше. Сначала боль с цифрой, потом демо, потом «почему агент».
- **Ничего не печатаем вживую** — только кнопки с заготовленными запросами.
- Показываем, какие инструменты вызывает агент: это лучшее доказательство агентности.
- Говорит один, кликает другой.
- Всегда есть запасное видео демо.
